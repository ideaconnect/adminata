## 0. Executive summary

1. The form layer is **three cooperating pieces**: (a) the Twig form theme `S/src/Resources/views/Form/form_admin_fields.html.twig` (extends Symfony's `form_div_layout.html.twig`, `S/…/form_admin_fields.html.twig:12`), (b) the edit page chrome `S/src/Resources/views/CRUD/base_edit_form.html.twig` + `base_edit_form_macro.html.twig`, and (c) ~1 100 lines of inline, per-field jQuery in `CRUD/Association/*.html.twig` + `Form/Type/sonata_type_model_autocomplete.html.twig`, plus the global `window.Admin` object (`S/assets/js/admin.js`) and four Stimulus controllers (`collection`, `edit`, `confirm_exit`, `sticky`).
2. Persistence bundles do **not** contain their own form markup; they only add dispatch blocks that `{% include '@SonataAdmin/CRUD/Association/edit_*.html.twig' %}` (`ORM/src/Resources/views/Form/form_admin_fields.html.twig:16-30`, `MONGO/src/Resources/views/Form/form_admin_fields.html.twig:17-27`). Therefore the **`@SonataAdmin` Twig namespace, the file paths under `CRUD/Association/`, and the Twig variables those templates read (`sonata_admin.*`, `btn_*`, `id`, `form`) are the hard compatibility contract**, not the CSS.
3. Server-side AJAX contracts (routes `sonata_admin_retrieve_form_element`, `sonata_admin_append_form_element`, `sonata_admin_short_object_information`, `sonata_admin_retrieve_autocomplete_items`; JSON `{result, objectId, objectName}`; 400 JSON violation list; `_xml_http_request` flag; `Accept: application/json`) are entirely PHP-side and can be kept byte-for-byte. Only the browser side (jQuery `ajaxSubmit`, Bootstrap 3 `.modal()`, select2, iCheck, jQuery-UI sortable) has to be rewritten.
4. Sonata already ships **Stimulus 3** via `@symfony/stimulus-bridge` with identifier prefix `sonata-` (`S/assets/js/stimulus.js:25-27`) and exposes `global.sonataApplication` (`S/assets/js/app.js:54`). form-extensions registers its `datepicker` controller onto that global (`FE/assets/js/app.js:156-160`). **Keep Stimulus as the JS backbone**; Alpine can coexist for TailAdmin chrome (sidebar/dark mode/dropdowns) but the form behaviours should be Stimulus controllers so that `data-controller`/`data-action` attributes and dispatched DOM events stay usable from user code.
5. The Bootstrap-3 grid vocabulary (`col-md-*`, `box box-primary`, `form-horizontal`, `col-sm-3`/`col-sm-9`) leaks into **PHP defaults and docs**: `BaseGroupedMapper::with()` defaults `box_class => 'box box-primary'` (`S/src/Mapper/BaseGroupedMapper.php:83`), the macro defaults `class` to `col-md-12` (`S/src/Resources/views/CRUD/base_edit_form_macro.html.twig:7`), docs tell users to pass `'class' => 'col-md-8', 'box_class' => 'box box-solid box-danger'` (`S/docs/reference/action_create_edit.rst:113-136`). adminata needs a **class-translation layer** (Twig filter) for these strings, or it will break every existing admin that customises groups.
6. Unit tests in Sonata pin Bootstrap markup literally (`S/tests/Form/AdminLayoutTest.php:31`, `:113`, `:148`, `:164`, `:178`; `S/tests/Form/Widget/FormChoiceWidgetTest.php:47`). These tests cannot be reused as-is; the user's fork's functional tests rely on `.field-container .sonata-ba-action[title="Add new"]` and `.modal-content button[name="btn_create"]` (`MONGO/tests/Functional/ReferenceMappingTest.php:35,61`, `EmbeddedMappingTest.php:52`) which **must keep working**.

The Twig side receives the option bag twice:

- `sonata_config.getOption('form_type')` — the `sonata.admin.configuration` service, arg 2 = `$config['options']` (`S/src/DependencyInjection/SonataAdminExtension.php:113`).
- `sonata_admin.options['form_type']` inside the form theme — from `FormTypeFieldExtension` whose second constructor arg is the same `$config['options']` (`SonataAdminExtension.php:208-210`; `S/src/Form/Extension/Field/Type/FormTypeFieldExtension.php:55,122`).

Note the unit test harness uses `form_type => 'vertical'` (`S/tests/Form/Widget/BaseWidgetTestCase.php:52-53`) and `'horizontal'` (`S/tests/Form/AbstractLayoutTestCase.php:120`); anything not equal to `'horizontal'` behaves as standard.

**Recommendation:** keep every key and default. Map `use_select2`/`use_icheck` to "enhance selects with Tom Select" / "render styled checkboxes" so that `false` still yields plain native controls (that is exactly what users disable them for, `S/docs/cookbook/recipe_select2.rst:10-25`, `recipe_icheck.rst:10-21`). Keep emitting `<meta name="sonata-config">` and `<meta name="sonata-translations">` with the same keys because `Config.param()`/`Translation.trans()` throw if the tag is missing (`S/assets/js/core/config.js:15-24`).

### 5.6 Rewrite design (keep contracts, drop jQuery/Bootstrap)

**One Stimulus controller `sonata-association`** attached to `div#field_container_{{id}}.field-container` with values: `fieldId`, `mode` (`list|standard|inline`), `multiple`, `retrieveUrl`, `appendUrl`, `shortDescriptionUrlTemplate` (with `OBJECT_ID`), `editUrlTemplate`, `modalTitle`, `placeholderText`, `loadingText`; targets `widget` (`#field_widget_…`), `actions`, `input` (`#{{id}}`), `editButton`, `modal`, `modalBody`, `modalTitle`. Implementation notes (all requirements derived from §5.3/5.4):

1. **Modal element**: keep `edit_modal.html.twig` as a TailAdmin overlay: `div#field_dialog_{{id}}.modal[hidden][role=dialog][aria-modal=true]` > backdrop + `div.modal-content.relative.w-[90vw].max-w-6xl.max-h-[85vh].flex.flex-col.rounded-3xl.bg-white.dark:bg-gray-900` > `div.modal-header.flex.items-center.justify-between.px-6.py-4.border-b > h4.modal-title` + close button > `div.modal-body.custom-scrollbar.flex-1.overflow-y-auto.p-6`. Keep ids/classes `modal-content`, `modal-title`, `modal-body` (the mongo fork's Panther test uses `.modal-content button[name="btn_create"]`, `MONGO/tests/Functional/ReferenceMappingTest.php:61`). Use a native `<dialog>` with `showModal()` **or** the overlay pattern — `<dialog>` gives focus trap/Escape for free and stacks cascaded modals correctly (top layer); the `dropdownParent` problem select2 had (`sonata_type_model_autocomplete.html.twig:81`) becomes a Tom Select `dropdownParent: 'body'` + top-layer z-index concern — with `<dialog>` the dropdown must be rendered *inside* the dialog (Tom Select default) to be visible. Still move the dialog to `document.body` on first open (nested forms).
2. **Fetching HTML**: `fetch(url, {headers:{'X-Requested-With':'XMLHttpRequest'}, credentials:'same-origin'})` → `modalBody.innerHTML = html` → **execute scripts** (`activateScriptElement` from `core/utils.js:85-95`; `innerHTML` does not run `<script>`, jQuery `.html()` did) → dispatch `sonata-admin-setup-list-modal` on the modal and re-run `Admin.shared_setup(modalBody)` (whatever adminata's version of it is, e.g. `document.dispatchEvent(new CustomEvent('sonata:enhance', {detail:{root}}))`). Stimulus controllers inside the injected HTML connect automatically (MutationObserver) — this is why Stimulus must remain the backbone.
3. **Submitting**: intercept `submit` on forms inside the modal body (event delegation on `modalBody`) and `click` on anchors that are not `.sonata-ba-action`, not `#`/`javascript:` (same filter as `:240-250,270-273`). Build `new FormData(form, submitter)`; append `_xml_http_request=1`; for anchors, GET `href` with the form's serialised data appended as query (`new URLSearchParams(new FormData(form))`) to preserve filter state like `ajaxSubmit` did. Headers: `Accept: application/json, text/html;q=0.9` for the create/edit POST (the controller only checks presence of `application/json` or `*/*`, `CRUDController.php:1375,1390`); for list navigation `Accept: text/html`. Do **not** set `Content-Type` manually with FormData.
4. **Response handling**: `response.headers.get('content-type')` starts with `application/json` → parse. `result === 'ok'` → close; list mode: set input value and fire `input.dispatchEvent(new Event('change', {bubbles:true}))`; other modes: POST the outer form (`new FormData(this.element.closest('form'))` + `_xml_http_request`) to `retrieveUrl`, replace `#field_container_{{id}}` with the response (`outerHTML`), select/check the new value, dispatch `sonata-admin-append-form-element` (bubbling CustomEvent — jQuery listeners bound with `jQuery(document).on(...)` still receive native bubbling events, so BC for user code holds as long as jQuery is present; without jQuery, document it as a native event). Status 400 JSON → violation injector (same DOM output as §3.1 #1). Status 406 → console error. HTML on 200 (e.g. preview) → inject.
5. **Short description refresh** on `change` of the hidden input: `fetch(shortDescriptionUrlTemplate.replace('OBJECT_ID', encodeURIComponent(value)))`, inject into `widgetTarget`, toggle `editButtonTarget.hidden` and update its `href` (replace the `.hidden` Bootstrap class with the `hidden` attribute — the base reset defines `[hidden]{display:none!important}` and `styles.scss:572-574` already had it).
6. **Global shims for BC**: keep the `onclick="return start_field_dialog_form_add_{{id}}(this)"` attributes and define the four `start_*`/`remove_selected_element_*` functions **once**, generically, in adminata's bundle JS: `window.start_field_dialog_form_add_<id>` cannot be generic, so instead emit a tiny inline script per field (`window['start_field_dialog_form_add_' + id] = (link) => sonata.association(link).openAdd()`) **or** drop the `onclick` attributes altogether and rely on `data-action`. Recommendation: drop `onclick`, keep the button markup (`a.sonata-ba-action[title]`) and the ids; document the removal of the global functions in UPGRADE notes (they were never documented API).
7. **Inline append** (`edit_one_script`): same controller, `append` action: POST outer form to `appendUrl`, parse HTML with `<template>`, move `input[type=file]` by id, replace container, set `enctype`, dispatch `sonata.add_element` (keep this exact event name; the sortable scripts listen to it) and `sonata-admin-append-form-element`.
8. **Disabled-submit reset**: `edit_controller.prepareSubmit` disables all `button`s 1 ms after submit (`edit_controller.js:27-32`); the modal error path must re-enable them (`:383-385,432`). Because the injected modal form has its own `sonata-edit` controller, disable/enable stays scoped per form.

## 14. Recommendations (implementation plan for this dimension)

1. **Keep PHP untouched** (types, extensions, mappers, actions, controller, routing, configuration). All work in this dimension is Twig + JS + CSS.
2. **Theme strategy**: adminata's `Form/form_admin_fields.html.twig` keeps every block and every `sonata-ba-*`/`form-group`/`has-error`/`help-block` hook and *adds* Tailwind utilities. Define Bootstrap-name aliases as Tailwind v4 `@utility` rules in the bundle CSS (`form-control`, `control-label`, `required`, `list-unstyled`, `input-group`, `input-group-addon`, `alert`, `alert-danger`, `btn`, `btn-*`, `box`, `box-*`, `hidden`, `checkbox`, `radio`) so that both adminata's markup and third-party templates (SonataMedia, SonataUser, form-extensions) render acceptably. Tailwind v4 `@utility` names can be arbitrary kebab-case, so this is cheap and keeps class lists short.
3. **Layout translation filters**: `sonata_grid_class`, `sonata_box_class` in a small Twig extension; use them in `base_edit_form_macro.html.twig` and `select_subclass.html.twig`.
4. **JS**: keep Stimulus + `stimulus-bridge` (Encore) or move to Vite with a manual `Application.start()` and `application.register('sonata-…')`; identifiers must stay `sonata-collection`, `sonata-edit`, `sonata-confirm-exit`, `sonata-sticky`, `datepicker`. Add `sonata-association` (modal/list/add/edit/remove/append), `sonata-autocomplete` (Tom Select remote), `sonata-select` (Tom Select for plain selects honouring `data-sonata-select2*`), `sonata-choice-field-mask`, `sonata-sortable` (SortableJS), `sonata-inline-row` (delete-checkbox error/required toggling), `sonata-dismiss` (alerts), `sonata-tabs` (or fold into `sonata-edit`). Provide `window.Admin` façade with the old method names and dispatch the old event names as bubbling `CustomEvent`s.
5. **Dependencies**: `tom-select`, `sortablejs`, `flatpickr`, `@hotwired/stimulus`, `alpinejs` (+ `@alpinejs/persist`) for TailAdmin chrome only. Drop `jquery`, `jquery-form`, `jquery-ui`, `bootstrap`, `admin-lte`, `icheck`, `select2`, `select2-bootstrap-theme`, `x-editable` (list dimension must replace x-editable), `jquery-slimscroll`, `masonry-layout`, `jquery.scrollto`, `@fortawesome/fontawesome-free` (icons become inline SVG; note `parse_icon`/`IconExtension` still emits `<i class="fas …">` for user-configured icons — assets dimension).
6. **Association templates**: rewrite the 18 `CRUD/Association/*.html.twig` markup with TailAdmin cards/tables/buttons; replace `edit_many_script.html.twig`/`edit_one_script.html.twig` contents with the Stimulus wiring (`data-controller`, values) so that the *include points* remain. Keep `edit_modal.html.twig` and always include it (also from the model-list widget instead of the inline copy).
7. **Datepicker**: override `sonata_type_datetime_picker_widget(_html)` in adminata's theme, ship a flatpickr `datepicker` controller with an options translator, and a format-token converter.
8. **Tests**: port `AdminLayoutTest`/`FormChoiceWidgetTest`/`FormSonataNativeCollectionWidgetTest` as adminata's own snapshot tests (update expectations), and add Panther e2e tests for: create via modal (list mode), select via list modal, inline collection add + sortable renumbering, autocomplete search + select + create-via-modal auto-select, choice field mask toggling, tab error focusing, confirm-exit — mirroring the mongo fork's `tests/Functional` harness (`MONGO/AGENTS.md` §6).

## 15. Open questions for the project owner

1. Should jQuery remain available as an **optional** global for user code (loaded only if `sonata_admin.assets.javascripts` includes it), or be removed entirely with a documented BC break for custom JS that used `jQuery(document).on('sonata-admin-append-form-element', …)` (native `CustomEvent`s bubble, so jQuery-bound listeners still fire if jQuery is present)?
2. Tom Select vs select2 4.1 for the autocomplete/multi-select layer — is preserving the `sonata_type_model_autocomplete_select2_options_js` override hook and select2 CSS hooks a requirement for any of your projects?
3. Horizontal form mode: keep emitting the legacy `col-sm-3`/`col-sm-9` class names alongside the grid utilities (test-compatible, noisier markup) or emit only the Tailwind grid (cleaner, breaks Sonata's `AdminLayoutTest` and user CSS that targets `.col-sm-9`)?

5. Should adminata be named `SonataAdminBundle` and `replace` `sonata-project/admin-bundle` in composer (so `@SonataAdmin` and service ids resolve without any consumer change), or register the `SonataAdmin` Twig namespace alias from a differently-named bundle?

7. form-extensions' Tempus Dominus assets: is it acceptable to require apps to not load `bundles/sonataform/app.js`, or should adminata remove it via `remove_javascripts` defaults?
8. Do any of your existing admins use `box_class`/`class` values outside the documented Bootstrap vocabulary (custom CSS classes) that the translation filter must pass through unchanged?
