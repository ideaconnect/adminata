# adminata research — PHP-side coupling to markup/CSS, the drop-in compatibility contract, docs impact

Scope: SonataAdminBundle 4.43.0 (`sonata-admin-4.43.0/`, tag commit 3fbcc80, 2026-06-03) compared with the `5.x` branch (`sonata-admin-5.x/`, commit d61788a "Merge 4.x into 5.x", 2026-06-04). All paths below are relative to the roots listed in the task unless prefixed. Line numbers are from the 4.43.0 tree (5.x is byte-identical except for three files, see §5).

Method: every `*.php` under `src/` was grepped for CSS class names, icon markup, Bootstrap/AdminLTE vocabulary and HTML fragments; each hit was read in context. The 131 Twig templates were only inspected for what they *consume* from PHP (config options, group/field options, list-mode metadata, x-editable attributes) and for the hook classes/blocks/ids that make up the user-facing surface. Docs were grepped for every instruction that tells users to write Bootstrap/AdminLTE/FontAwesome/jQuery code. The persistence bundles (doctrine-orm-admin-bundle latest, the user's `idct/sonata-admin-mongodb-bundle`), form-extensions 2.7.0 and block-bundle 5.4.0 were checked for what they assume about the admin-bundle's markup.

---

## 0. Executive summary

1. **PHP-side markup coupling is small and enumerable** — 20-odd literal strings in ~12 files (table in §1). Nothing in `src/*.php` generates Bootstrap grid or component markup except (a) `IconRuntime::parseIcon()` which emits `<i class="fa* …" aria-hidden="true"></i>` and *rejects* any non-FontAwesome, non-HTML icon string (`src/Twig/IconRuntime.php:22-37`), (b) three default option values (`box_class` = `box box-primary`, dashboard block `class` = `col-md-4`, stats block `color` = `bg-aqua`), (c) two KnpMenu attributes (`nav navbar-nav`, `keep-open`), (d) the AdminLTE skin stylesheet path composed in the DI extension (`src/DependencyInjection/SonataAdminExtension.php:93-99`), and (e) the `sonata-medium-date` form `attr.class` default (`src/DependencyInjection/SonataAdminExtension.php:198-206`).
2. **The 5.x branch is not a "cleaned" major yet.** `diff -rq` between the two `src/` trees (excluding views) yields exactly 3 files, all about making `AdminExtensionInterface::preBatchAction()` mandatory and adding a `?string` return type to `CRUDController::handleModelManagerThrowable()`. `tests/` is identical, `composer.json` is identical, `src/BCLayer/BCHelper.php` still exists in both, and 189 `NEXT_MAJOR` markers in 63 files remain in both. `UPGRADE-5.0.md` contains one section. There is nothing to gain from forking 5.x; there is something to lose (mandatory `preBatchAction` breaks third-party extensions such as `runroom/sortable-behavior-bundle` that implement the interface directly).
3. **"Drop-in" for the persistence bundles is only achievable if adminata keeps the bundle class name `Sonata\AdminBundle\SonataAdminBundle`, the Twig namespace `@SonataAdmin`, the package name via `composer replace: sonata-project/admin-bundle`, and the `sonata.admin.*` service ids.** Both `doctrine-orm-admin-bundle` and the user's Mongo fork (a) `require: sonata-project/admin-bundle ^4.39`, (b) `{% extends '@SonataAdmin/Form/form_admin_fields.html.twig' %}` and `{% include '@SonataAdmin/CRUD/Association/edit_*.html.twig' %}` from their own form themes, (c) look up `sonata.admin` tags with `manager_type`, and (d) get `sonata.admin.manager.<type>`, `sonata.admin.builder.<type>_form|show|list|datagrid`, `sonata.admin.data_source.<type>`, `sonata.admin.field_description_factory.<type>` injected by name (`src/DependencyInjection/Compiler/AddDependencyCallsCompilerPass.php:356-370`).
4. **The user-facing compatibility surface that *cannot* be kept byte-for-byte is the Bootstrap 3 class vocabulary in user-land templates and options** (`box box-primary`, `col-md-6`, `btn btn-sm`, `label label-primary pull-right`, `nav navbar-nav`, `bg-aqua`). §3 proposes a small opt-in `compat.css` layer built with Tailwind `@utility`/`@apply` that keeps the *common* ones rendering sensibly, and lists what must be documented as a break.
5. **Docs**: 13 reference pages, 5 getting-started pages and 8 cookbook recipes contain Bootstrap/FA/jQuery-specific instructions (§4). Three recipes (`recipe_bootlint`, `recipe_icheck`, `recipe_jquery_ui`) describe features that cease to exist.

### 2.5 The `@SonataAdmin` namespace and `templates/bundles/SonataAdminBundle/` overrides

Facts: 89 `@SonataAdmin/...` references across 61 of the 131 templates; ORM and Mongo form themes `extends '@SonataAdmin/Form/form_admin_fields.html.twig'` and `include '@SonataAdmin/CRUD/Association/edit_*.html.twig'`; block-bundle's `sonata_block.templates.block_base` is extended by `Block/block_admin_list.html.twig:12`.

Decision: **keep bundle name → keep `@SonataAdmin`.** Consequences to document:

* Any user override under `templates/bundles/SonataAdminBundle/**` will *still be picked up* — and will be **Bootstrap markup dropped into a Tailwind page**. This is the single largest "drop-in" hazard. Mitigation: (1) ship `compat.css` (§3) so common Bootstrap classes degrade gracefully; (2) ship a console command `adminata:audit-overrides` that lists overridden templates and greps them for Bootstrap classes / `{% block %}` names that no longer exist; (3) keep **all 138 block names** (§2.6) so partial overrides still slot in.
* Users extending `@SonataAdmin/standard_layout.html.twig` and overriding `stylesheets`/`javascripts` blocks keep working; those overriding `body_attributes` to add AdminLTE classes (`sidebar-mini`, `skin-*`, `fixed`) must be told those are ignored.
* Users who rely on AdminLTE JS (`$.AdminLTE`, `data-widget="tree"`, `data-toggle="push-menu"`) in their own templates lose it — no shim possible.

## 5. Fork base: 4.43.0 vs 5.x

Evidence:
* `diff -rq sonata-admin-4.43.0/src sonata-admin-5.x/src -x views` → 3 files: `src/Admin/AbstractAdminExtension.php` (docblock removed), `src/Admin/AdminExtensionInterface.php` (`preBatchAction()` uncommented → **mandatory**), `src/Controller/CRUDController.php` (`method_exists` guard removed; `handleModelManagerThrowable(): ?string`).
* `diff -rq …/tests` → empty; `composer.json` identical (same `branch-alias`, same PHP `^8.2`, Symfony `^6.4||^7.3||^8.0`); `UPGRADE-5.0.md` contains a single "preBatchAction" section; `src/BCLayer/BCHelper.php` present in both; 189 `NEXT_MAJOR` markers / 63 files in both; CHANGELOG identical (5.x last merge 2026-06-04, one day after 4.43.0).
* `phpstan-baseline.neon`, `rector.php`, assets, docs identical.

Recommendation: **fork from 4.43.0** (the tag), version adminata as `1.0.0` with `replace: sonata-project/admin-bundle: 4.43.0` (so `^4.39` constraints of ORM/Mongo bundles resolve). Reasons: (1) 5.x offers no cleanup to inherit; (2) the one 5.x change is a BC break for third-party `AdminExtensionInterface` implementors (runroom sortable bundle, SonataDoctrineORM's own extensions implement `AbstractAdminExtension` so they're fine, but user code that implements the interface directly is not); (3) keeping 4.x semantics lets adminata claim "4.43-compatible" honestly and lets the Mongo fork keep `^4.39`. Adminata can still *apply* the 5.x `handleModelManagerThrowable(): ?string` return type (pure PHP, no BC impact for subclasses? — it *is* a BC break for subclasses lacking the return type; skip). Cherry-pick 4.x point releases forward as they appear (the diff surface is small and mostly PHP).

Housekeeping to do at fork time (does not affect compat): raise `php` to `^8.4` to match the Mongo fork's floor (`AGENTS.md` §4) — but note the ORM bundle allows `^8.2`, so adminata's floor only constrains end users; keep Symfony `^7.4 || ^8.0`; drop `MopaBootstrapBundle` detection; drop `sonata.admin.form.filter.type.*` deprecated filter form types? (No — persistence bundles still reference `FilterDataType` only, but user code may reference the old ones; keep until adminata 2.0.)

## 6. Risks and open questions

Risks (severity in parentheses):
1. **User template overrides in `templates/bundles/SonataAdminBundle/` silently render Bootstrap markup in a Tailwind page** (high). Mitigation: compat.css on by default in 1.0 + `adminata:audit-overrides` command + docs.
2. **Third-party Sonata bundles (SonataMedia, SonataUser, SonataPage, SonataBlock templates, runroom sortable) ship Bootstrap 3 + jQuery templates and call `window.Admin.*` / `$.fn.*`** (high). Mitigation: compat.css + `window.Admin` facade + `data-toggle` handlers; state explicitly which bundles are verified.
3. **`IconRuntime::parseIcon()` throws on non-FA icons** — any new icon syntax must be additive and the FA fallback must stay, or every existing YAML `icon:` breaks (medium). Tests fix the exact `<i>` HTML.
4. **`SonataAdminExtension.php:93-99` unconditionally appends the AdminLTE skin CSS path** — must be removed or the page 404s an asset (low, but easy to miss).
5. **`bundles/sonataform/app.css` (Bootstrap-styled tempus-dominus) is in the default asset list and form-extensions registers its datepicker theme globally** (medium). Adminata must override date/time widgets in its form theme (it already does) and drop the sonataform assets from the defaults; users who copy-pasted the full default `assets:` list will still load them → harmless but bloated; document.
6. **x-editable, select2, iCheck, masonry, sortable, slimscroll behaviours must be re-implemented against the *same* `data-*`/JSON contracts** (§2.8, §2.11) — inline edit and autocomplete are core features (high effort, contract is clear).
7. **Compat layer name collisions with Tailwind utilities**: `fixed`, `collapse`, `hidden`, `container`, `block`, `table`, `label`?, `sr-only`, `truncate` — must not be redefined; `.table` in Tailwind is `display:table` which is compatible with Bootstrap's `.table` semantics only partially (medium; test visually).
8. **Tests**: ~4.3k lines of exact-HTML fixtures in RenderElement tests will all change; plan for a fixture regeneration workflow rather than hand edits (medium).
9. **`composer replace` semantics**: with `replace`, Composer will refuse to install `sonata-project/admin-bundle` alongside; Packagist will not show adminata as a provider unless the replace version matches constraints — pin `replace` to a concrete `4.43.0` (or `4.99.0` to satisfy future `^4.44` bumps in persistence bundles) (low).
10. **`form_type: horizontal` + Mopa `horizontal_*_class` options** rely on Bootstrap grid class strings — keep options, map through compat grid (low).
11. **`dropdown_number_groups_per_colums` typo and `label_catalogue` deprecations**: keep as-is; adminata 2.0 cleans (low).
12. **Functional tests in the Mongo fork use Panther and select on Sonata DOM** (`tests/Functional/BasePantherTestCase.php`) — they will need selector updates if they rely on Bootstrap classes rather than `sonata-ba-*` hooks (medium; verify).

Open questions for the project owner:
1. Package/versioning: adminata `1.0.0` + `replace: sonata-project/admin-bundle: 4.43.0`, or continue the `4.x` numbering (`4.43.0-adminata.1`) so `^4.39` constraints stay obviously satisfied?
2. Should adminata keep the `Sonata\AdminBundle\` PHP namespace for *everything* (recommended) or only for the contract classes, with new code under `Idct\Adminata\`?
3. Icon strategy: ship FontAwesome 5 webfont for compatibility (bigger, zero break) vs SVG sprite with a finite map (smaller, breaks unknown `fa-*` names)?
4. Should `compat.css` be loaded by default in 1.0 (safer for drop-in) or opt-in (cleaner pages)?
5. Is `use_select2`-style "enhanced select" wanted at all (Tom Select is MIT, ~40 KB), or plain native selects + the ajax autocomplete combobox only?
6. Which third-party Sonata bundles must be verified working (SonataUser? SonataMedia? SonataBlock only?) — this decides how much of the `window.Admin` jQuery facade is needed.
7. Do we keep `form_type: horizontal`?
8. `theme` config: `light|dark|system` + brand colour via `@theme` tokens at build time, or runtime CSS variables so users can theme without a Node build?
9. Should adminata drop `bundles/sonataform/*` from the default asset list (recommended) even though form-extensions still ships them?
10. PHP floor: `^8.4` (matching the Mongo fork and its `final readonly`/property-hook conventions) or `^8.2` (matching ORM bundle)?
