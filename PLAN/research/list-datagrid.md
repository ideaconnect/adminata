# adminata research — List view, datagrid, filters, pager, batch, inline editing, tree/mosaic

Scope: everything Sonata Admin 4.43.0 renders for the `list` action and its ancillary views, and what each piece becomes when the Twig templates and assets are rebuilt on Tailwind CSS v4 + TailAdmin v2.3.0 while keeping the PHP API, service ids, config keys, template keys and Twig block names intact.

All paths are relative to the roots given in the task. `SA/` = `sonata-admin-4.43.0/`, `TA-html/` = `tailadmin-html/`, `TA-react/` = `tailadmin-react/`, `TA-next/` = `tailadmin-next/`, `ORM/` = `vendor-extract/doctrine-orm-admin-bundle/sonata-project-SonataDoctrineORMAdminBundle-2147390/`, `FE/` = `vendor-extract/form-extensions/`, `MONGO/` = `/home/bartosz/dev/idct/sonata-admin-mongodb-bundle/`.

Verified facts that frame everything below:

- The 5.x dev branch views are byte-identical to 4.43.0 (`diff -rq SA/src/Resources/views sonata-admin-5.x/src/Resources/views` prints nothing; both have 80 files under `CRUD/`), so nothing in this dimension needs to diverge for 5.x readiness.
- `assets/js` and `package.json` of 5.x are also identical to 4.43.0 (same jQuery 3.7 / Bootstrap 3.3 / AdminLTE 2.4 / x-editable / select2 / iCheck stack; `sonata-admin-5.x/package.json:1-24`). The JS rewrite is therefore fully ours to design.
- The per-type list template map lives in the core, not in the persistence bundles: `SA/src/Templating/TemplateRegistryInterface.php:52-75` (`LIST_TEMPLATES`) and is injected into `sonata.admin.builder.orm_list` / `sonata.admin.builder.doctrine_mongodb_list` via `SA/src/DependencyInjection/AbstractSonataAdminExtension.php:40-41`. The ORM and Mongo `ListBuilder`s only hard-code `@SonataAdmin/CRUD/list__action.html.twig` and `@SonataAdmin/CRUD/list__action_%s.html.twig` (`ORM/src/Builder/ListBuilder.php:132,139`; `MONGO/src/Builder/ListBuilder.php:112,127`) and, for ORM, the four `Association/list_*.html.twig` fallbacks (`ORM/src/Builder/ListBuilder.php:100-118`). Consequence: **template names under `@SonataAdmin/CRUD/` are a hard public contract with both persistence bundles** and must keep their paths.

## 4. Inline editing (x-editable) — contract and replacement

### 4.1 Current client flow (`assets/js/admin.js:191-212`)

`Admin.setup_xeditable(subject)` runs `$('.x-editable', subject).editable({ emptyclass: 'editable-empty btn btn-sm btn-default', emptytext: '<i class="fas fa-pencil-alt"></i>', container: 'body', placement: 'auto', success(response){ html=$(response); Admin.setup_xeditable(html); $(this).closest('td').replaceWith(html) }, error(xhr){ JSON if Content-Type json else responseText } })`. It runs on page load through `shared_setup` (`:20-28`) and on modal content after AJAX (`edit_many_script.html.twig:53,94,128`). CSS: `styles.scss:410-440` (`.editable` pointer, `.editable-empty` hidden until row hover, `.editable-pre-wrapped`). Bootstrap-3 x-editable (`app.js:29`) renders a Bootstrap popover with the input, OK/Cancel buttons, inline validation error.

x-editable POSTs `application/x-www-form-urlencoded` with `name`, `value` (array for checklist), `pk` to `data-url` via jQuery AJAX (so `X-Requested-With: XMLHttpRequest` is set).

### 4.3 Proposed replacement: `sonata-editable` Stimulus controller with a Tailwind popover

## 9. Icons

Every list template uses FontAwesome 5 `<i class="fas fa-…">`: filter (`fa-filter`), `fa-minus-circle`, `fa-cogs`, `fa-arrow-circle-right`, `fa-share-square`, `fa-arrow-circle-o-down` (a FA4 name that does not exist in FA5 — renders nothing today), `fa-pencil-alt`, `fa-eye`, `fa-history`, `fa-times`, `fa-check`, `fa-caret-right`, `fa-code`, `fa-magic`, `fa-list`, `fa-th-large`, plus the `<i class="far">` placeholder in filter entries and user-supplied `label_icon` / list-mode `icon` strings validated by `IconRuntime::parseIcon` (`fa|fas|far|fab|fal|fad` prefixes only, or raw `<…>`). TailAdmin ships inline SVGs only (`TA-html/src/js/index.js` imports no icon font).

Options: (a) keep `@fortawesome/fontawesome-free` CSS in the adminata bundle for BC (simplest; SVG for Sonata's own templates, FA for user-provided classes), or (b) make `IconRuntime::parseIcon` map known `fa-*` names to a bundled SVG sprite (`<svg><use href="#fa-list">`) and fall back to `<i class>` — the public exception behaviour (`InvalidArgumentException` for unsupported formats) must be preserved either way. `DEFAULT_LIST_MODES` icons are raw `<i>` HTML (constant, §2.5), so (b) must also handle already-rendered `<i class="fas …">` strings (string starts with `<` → returned unchanged), i.e. the layout should run them through a `fa_to_svg` filter or accept FA CSS.
